# Despliegue manual del backend Firebase del POS

El workflow **Desplegar backend Firebase del POS** se ejecuta desde Actions mediante **Run workflow**. Su único destino es `punto-de-venta-comic-shop`. Cada ejecución autoriza un solo componente y un SHA completo de `main`, después de pasar las pruebas de ese commit. Las reglas se cargan mediante `firestore:rules` y la única función admitida es `procesarVentaPos`. La PWA, Firebase Hosting y los datos del negocio se gestionan aparte.

## Configuración manual inicial

1. En GitHub crea el entorno `firebase-produccion` en **Settings → Environments**. Restringe las ramas de despliegue a `main`, protege esa rama y habilita revisión obligatoria en el entorno si tu plan lo permite. Deja vacías las variables de autorización `POS_FIREBASE_FUNCION_SHA` y `POS_FIREBASE_REGLAS_SHA`. Cada una se completará por separado cuando apruebes un despliegue.
2. En Google Cloud Console selecciona el proyecto existente **punto-de-venta-comic-shop** y copia su número del proyecto. Comprueba que Firestore `(default)` está en modo Native y que la ubicación admite el disparador de la Function en `us-central1`, la región predeterminada del código. Si necesitas otra región, revisa la configuración de la Function antes de autorizar. Verifica los servicios de IAM Credentials, Security Token Service, Firebase, Firebase Rules, Firestore, Cloud Functions, Cloud Run, Cloud Build, Artifact Registry, Eventarc y Pub/Sub. Si debes habilitar alguno, verifica el identificador de proyecto antes de hacerlo.
3. En ese mismo proyecto crea la cuenta de servicio **`pos-github-deploy`**, con correo `pos-github-deploy@punto-de-venta-comic-shop.iam.gserviceaccount.com`. Para Firebase CLI configura `roles/firebase.viewer`, `roles/serviceusage.serviceUsageConsumer`, `roles/firebaserules.admin` y, para Functions, `roles/cloudfunctions.admin`, según la guía de permisos de Firebase. Limita `roles/iam.serviceAccountUser` a las identidades de ejecución y compilación efectivamente usadas. Verifica antes la identidad de ejecución gen 2 y sus permisos Firestore (`roles/datastore.user`) y Eventarc (`roles/eventarc.eventReceiver`). El invocador debe poder llamar al servicio Cloud Run de la Function. Verifica las identidades de servicio administradas y los permisos de compilación que exige el proyecto. Mantén sin asignar los roles globales Owner y Editor. [Permisos de Firebase](https://firebase.google.com/docs/projects/iam/permissions/) · [Permisos de Eventarc](https://docs.cloud.google.com/eventarc/standard/docs/functions/roles-permissions)
4. Crea un pool WIF `pos-github` con proveedor OIDC `github` e issuer `https://token.actions.githubusercontent.com`. En el mapeo configura `google.subject=assertion.sub` y `attribute.repository_id=assertion.repository_id`. Restringe el proveedor con esta condición. Coteja los IDs numéricos con el repositorio y su propietario antes de guardar.

   ```text
   assertion.repository_id == '1455596931' &&
   assertion.repository_owner_id == '346373337' &&
   assertion.ref == 'refs/heads/main' &&
   assertion.event_name == 'workflow_dispatch' &&
   assertion.environment == 'firebase-produccion' &&
   assertion.workflow_ref == 'kdnaskrlos/Punto-de-Venta/.github/workflows/desplegar-firebase-pos.yml@refs/heads/main'
   ```

   Concede `roles/iam.workloadIdentityUser` **en la cuenta `pos-github-deploy`** al principal:
   `principalSet://iam.googleapis.com/projects/NUMERO_PROYECTO/locations/global/workloadIdentityPools/pos-github/attribute.repository_id/1455596931`.
   En el entorno de GitHub guarda las variables `POS_FIREBASE_PROJECT_NUMBER` y `POS_FIREBASE_WIF_PROVIDER` con el formato `projects/NUMERO_PROYECTO/locations/global/workloadIdentityPools/pos-github/providers/github`. Son identificadores públicos. El workflow obtiene credenciales efímeras por OIDC. [Autenticación WIF para GitHub Actions](https://github.com/google-github-actions/auth#workload-identity-federation-through-a-service-account) · [Claims de OIDC](https://docs.github.com/en/actions/reference/security/oidc)
5. Revisa el repositorio `gcf-artifacts` de Artifact Registry y su política antes de autorizar Functions. El CLI no interactivo puede reportar un fallo de política después de haber actualizado la Function. Si ocurre, verifica la versión activa antes de reintentar. Cualquier política de limpieza que pueda eliminar imágenes existentes necesita revisión y autorización propias. Define alertas de presupuesto. Para limitar el costo inicial, conserva cero instancias mínimas y revisa retención de artefactos de compilación y logs. Una alerta informa del consumo y no detiene el servicio. [Precios de Firestore](https://firebase.google.com/docs/firestore/pricing)

## Autorización y compatibilidad

- Antes de autorizar, inventaría en modo de solo lectura las reglas vigentes, la ubicación, cualquier Function con el mismo nombre y las solicitudes de venta ya existentes. Conserva la revisión anterior y su configuración para revertir. El desencadenador de creación observa solicitudes nuevas. Las solicitudes anteriores requieren una revisión explícita y conservar su ID.
- Con el código aprobado en `main` y los controles de identidad listos, establece **solo** la variable SHA del componente aprobado y usa el mismo SHA como parámetro de **Run workflow**, rama `main`. Tras verificar la ejecución, retira esa autorización del entorno.
- Para preparar la venta procesada, primero comprueba la Function y luego revisa las reglas compatibles. El cliente de piloto habilita `firebaseConfig.ventasAtomicas`; el despliegue del backend no cambia la configuración del cliente público. La ruta histórica queda abierta por defecto. Prueba 10, 15, 20 y 30 SKU, pagos y descuentos, faltantes, duplicados y la recuperación offline en PC y Android. En el proyecto existente, cualquier prueba remota exige una autorización separada y una cuenta sintética exclusiva. Los permisos WIF del workflow no se usan para esa matriz. [Validación final](VALIDACION-FINAL-V243.md)
- El interruptor `sistema/estado.soloVentasProcesadas` es un paso posterior. Antes de habilitarlo, comprueba que todas las instalaciones tienen el cliente procesado y concilia cada cola anterior. El interruptor impide la creación directa de ventas ordinarias. Apartados, abonos y liquidaciones históricas de comisiones conservan sus controles previos y requieren una revisión y decisión separadas. El workflow no cambia este interruptor.
- Los casos históricos 04 y 05 de pestañas que ejecutan v2.35 se registran como limitaciones conocidas. La CI exige que los demás casos pasen. Aplica la migración supervisada para proteger los borradores antes del cambio. [Recuperación PWA](RECUPERACION-PWA.md)
- Si debes revertir, detén nuevas operaciones y concilia pendientes con sus IDs originales. Autoriza una revisión de reversión en `main` para el componente afectado. Restaura reglas y Function en el orden que permita resolver las solicitudes pendientes. Evita eliminar datos o repetir cobros al recuperar una versión anterior.
